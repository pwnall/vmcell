# Designing "Imp-Harness": An End-to-End Micro-VM Integration/Evaluation Platform in Rust

## TL;DR
- **Use Cloud Hypervisor (Apache-2.0/BSD-3-Clause, pure Rust) as the primary VMM, driven from Rust as a subprocess over its `--api-socket` REST API**, because it is the only mature Rust-native VMM that natively supports the three independently-permissioned virtio-fs mounts you need plus virtio-vsock and TAP networking. Firecracker is the well-justified alternative for maximum density/boot speed, but it deliberately does **not** support virtio-fs (shared dirs must be emulated via block devices or vsock), which makes your three-mount requirement awkward.
- **RAM is indeed the binding constraint.** VMM overhead is tiny (Firecracker's CI-enforced spec is ≤5 MiB VMM-thread overhead per microVM) but the *guest* footprint dominates: a usable minimal Debian guest realistically needs ~128–256 MiB. With KSM + a read-only shared rootfs + virtiofs `cache=never`, a 128 GB host can realistically run on the order of several hundred concurrent micro-VMs at 256 MiB each before RAM (not vCPU) saturates; one virtiofsd process per VM and TAP/bridge scaling are the next limits.
- **Recommended stack:** Cloud Hypervisor + a minimal Debian Trixie rootfs built with `mkosi` (debootstrap backend) + a custom minimal `vmlinux` (PVH/direct-kernel boot) + virtiofsd (one per VM, three tags with per-mount `--read-only`) + virtio-vsock for host↔guest control + TAP into an nftables `REDIRECT` transparent proxy for logged/filtered egress. Drive lifecycle from Rust via the `cloud-hypervisor-client` crate (or your own thin OpenAPI client); enforce limits and cleanup via cgroups v2.

## Key Findings

### VMM choice
- **Cloud Hypervisor** is written in Rust on the rust-vmm crates, supports x86_64 and aarch64 (riscv64 experimental), has native built-in virtio-fs (`--fs`), virtio-vsock (`--vsock`), TAP networking (`--net`), virtio-block, and snapshot/restore (incl. userfaultfd lazy restore as of v52). It is licensed Apache-2.0/BSD-3-Clause (per the repo's CONTRIBUTING.md: "licensed under the Apache v2 License and the BSD 3 Clause license … New code should be under the Apache v2 License"). **It is intended to be run as a subprocess and controlled over a REST or D-Bus API socket — it is NOT published as an embeddable library crate.** This is the single most important architectural caveat; the in-repo docs/api.md states the CLI "can not be used for controlling the VMM or the launched VM once they're up and running … you must use the REST API." Both Kata's `clh` integration and libvirt drive it as a child process.
- **Firecracker** (Apache-2.0, Rust) is the density/speed champion. Per its official `SPECIFICATION.md`: "Firecracker's virtual machine manager threads have a memory overhead <= 5 MiB … tested as part of the Firecracker CI using a memory cop," and "It takes <= 125 ms to go from receiving the Firecracker InstanceStart API call to the start of the Linux guest user-space /sbin/init process … measured using a VM with the serial console disabled and a minimal kernel and root file system." The official site adds it "supports microVM creation rates of up to 150 microVMs per second per host." But it exposes only 5 emulated devices (virtio-net, virtio-block, virtio-vsock, serial, a minimal keyboard controller) and **deliberately rejects virtio-fs** for attack-surface reasons (maintainers: "We still think the attack surface implications are large. Even in read-only mode, it's still a lot of code"). No filesystem passthrough means your three shared mounts must be modeled as pre-formatted block devices (no hotplug) or shuttled over vsock.
- **Dragonball** is a Rust-native VMM built *into* Kata's runtime-rs as a library — the most genuinely "embeddable" Rust option — but it is coupled to the Kata ecosystem and not designed for standalone third-party embedding.
- **libkrun** (Apache-2.0) is a genuinely embeddable dynamic library with a C API, incorporating Firecracker/rust-vmm/Cloud Hypervisor code; supports virtio-fs and a novel "TSI" (Transparent Socket Impersonation) networking mode. Good for tight in-process integration but requires its custom kernel (libkrunfw) and a C FFI boundary.
- **QEMU microvm** (GPL-2.0) is the most compatible baseline with the best nested-virt support and full device model, but it is C (GPL — acceptable to you as readable/documentation only) and slower to start than the lightweight VMMs.
- **rust-vmm** is the crate toolbox (kvm-ioctls, kvm-bindings, vm-memory, virtio-queue, vhost, vhost-user-backend, linux-loader, vm-superio, event-manager, vmm-sys-util) underlying all the above; building a bespoke VMM is possible but is a large undertaking versus using Cloud Hypervisor.

### Functional-requirement coverage
All six requirements map cleanly onto Cloud Hypervisor; only nested virt is a Firecracker weakness, and it's a nice-to-have.

## Details

### A. Rust library availability & maturity per technology

**Cloud Hypervisor.** Driven as a subprocess over `--api-socket`. From Rust, use the `cloud-hypervisor-client` crate (an unofficial, auto-generated OpenAPI client — its README states "auto-generated from the OpenAPI description for the cloud-hypervisor REST API using OpenAPI Generator"; latest 0.3.3, MIT OR Apache-2.0) or generate your own from the in-repo OpenAPI spec `vmm/src/api/openapi/cloud-hypervisor.yaml`. The `ch-remote` binary is the first-party control tool and supports `add-fs`, `add-net`, `add-vsock`, `add-disk`, `snapshot`, `restore`, `pause`, `resume`, `info`, `counters`, `shutdown`. Lifecycle (create/boot/pause/snapshot/restore/delete/shutdown) is all exposed over REST. Live resource counters are available via the `counters` API; combine with host cgroups v2 for authoritative RAM/CPU/IO.

**Firecracker.** Several Rust SDKs exist: `firecracker-rs-sdk` (pure Rust, manages firecracker + jailer), `firec`, `firepilot` (OpenAPI-model-based), `fctools`, plus the auto-generated `firecracker-http-client`. All drive the REST API over the unix socket; Firecracker is also a subprocess (one process = one microVM), not a library.

**Dragonball.** Rust library inside `kata-containers/src/dragonball`; embeddable in principle but Kata-coupled.

**Monitoring.** No VMM exposes everything; the right approach is cgroups v2 on the host (put each VMM process in its own cgroup; read `memory.current`, `memory.peak`, `cpu.stat`, `io.stat`). Rust crates: `cgroups-rs` (cgroup v2 support, builder API, MIT/Apache-2.0), `controlgroup` (v1-focused), or read `/sys/fs/cgroup/...` directly. For per-process sampling, `sysinfo` or `perf_monitor`.

### B. Required build artifacts
- **Kernel:** an uncompressed `vmlinux` with a PVH entry point for direct kernel boot (no BIOS/bootloader). Cloud Hypervisor and Firecracker both boot `vmlinux` via the Linux/PVH boot protocol; QEMU microvm boots PVH ELF images. Start from Firecracker's recommended minimal kernel config or Cloud Hypervisor's config and trim drivers to cut boot time. Depot's engineering write-up identifies direct kernel boot with a trimmed minimal config as "the biggest single optimization for microVM boot times," letting you "swap the stock Ubuntu kernel for one compiled from a minimal config … [cutting] out drivers, modules, and filesystems you don't actually need." (Depot's reported boot-time deltas vary by article and baseline — treat the magnitude as illustrative and re-measure.)
- **Firmware/BIOS:** none for direct kernel boot (this is the fast path). QEMU microvm uses qboot/SeaBIOS only if needed; EDK2/OVMF only if you must boot a distro EFI image.
- **Rootfs:** raw ext4 image (Firecracker requires pre-formatted block images; no hotplug). For Cloud Hypervisor + virtiofs you can serve a host directory directly (no image needed) or use virtio-block. Consider squashfs (read-only, compressed) for the shared base rootfs and an overlay for writes.
- **Reproducibility:** `mkosi` (systemd project) builds Debian images reproducibly via debootstrap, supports `--ephemeral`, virtiofs directory output, and minimal package sets. Licenses of the toolchain (mkosi, debootstrap, virtiofsd) are permissive/Free; virtiofsd is "Apache-2.0 AND BSD-3-Clause."

### C. Guest distro / rootfs
- Debian Trixie is fine. Build a **minimal** rootfs with `mkosi` (Distribution=debian, Release=trixie) including only what the test needs; the built-in `mkosi-vm` profile adds the packages needed to boot. Strip to: no display manager, minimal systemd (or a custom PID1 / no init for the most ephemeral tests), serial console agetty only if you need interactive debugging.
- For the fastest/smallest guests, compare against a custom minimal init: the Firecracker docs demonstrate an Alpine+OpenRC rootfs and even a bare `/sbin/init` ELF ("The minimal init system would be just an ELF binary, placed at /sbin/init"). A static "agent" binary as PID1 (talking vsock) is the lowest-overhead option for seconds-to-minutes ephemeral tests.
- Init choice: systemd (compatible, heavier and slower), vs. a minimal init, vs. no init (your agent as PID1). For a test harness, a small Rust agent as PID1 over vsock is ideal: fastest boot, lowest RAM, direct control channel.

### D. Snapshotting / fast clone
- **Firecracker:** mature. Snapshot = state file + memory file; restore uses `MAP_PRIVATE` of the memory file → on-demand page loading, copy-on-write to anonymous memory, with optional userfaultfd handler. The docs note "The design allows sharing of memory pages and read only disks between multiple microVMs … Shares clean pages across multiple VMs" — a real memory-density win. Requires VMGenID/entropy reseeding to keep clones unique (see Brooker et al., "Restoring Uniqueness in MicroVM Snapshots," arXiv 2102.12892).
- **Cloud Hypervisor:** pause→snapshot→restore→resume; v52 added userfaultfd lazy memory restore and sparse (SEEK_DATA/SEEK_HOLE) snapshot files. Not guaranteed across versions.

### Concurrency & RAM-density analysis
- **VMM overhead vs guest footprint.** Firecracker guarantees ≤5 MiB VMM-thread overhead for a 1-vCPU/128-MiB microVM (CI-enforced via a "memory cop"; the spec warns it is workload-dependent — "a workload with multiple vsock connections might generate a memory overhead > 5MiB"). That is the *VMM* cost; the *guest* RAM you allocate (128–256 MiB+ for a usable Debian userland) dominates total consumption.
- **Density techniques:**
  - **KSM (kernel samepage merging):** merges identical pages across VMs. The original Red Hat KSM experiment (per the Linux 2.6.32 changelog) "found that 52 virtual instances of Windows XP with 1 GB of memory, could run on a host computer that had only 16 GB of RAM." More recently, Stefan Roesch (Meta) reported at the 2023 Linux Plumbers Conference (via LWN) "a savings of around 6GB of memory on a 64GB machine," with process-level KSM enabling "a capacity increase of around 20%." Costs ~5–10% CPU for `ksmd` scanning; set `merge_across_nodes=0` on NUMA. Most effective when many guests run identical rootfs/kernel.
  - **Snapshot COW / clones:** boot one golden microVM, snapshot, restore N clones sharing clean pages copy-on-write — large density and latency win.
  - **virtiofs `cache=never` + shared read-only rootfs:** Per cloud-hypervisor/docs/fs.md, "The cache=never option is the default when using virtiofsd with Cloud Hypervisor. This prevents from using the host page cache, reducing the overall footprint on host memory. This increases the maximum density of virtual machines that can be launched on a single host." The DAX window additionally lets guests map host page cache directly, further cutting footprint.
  - **virtio-balloon / free-page reporting:** reclaim unused guest RAM back to host.
- **Realistic counts (must re-benchmark on your hardware):** at 256 MiB/guest, a 64 GB host ≈ ~200 VMs, 128 GB ≈ ~450 VMs, 256 GB ≈ ~900 VMs, before accounting for host reserve and overheads; KSM + shared rootfs can push these meaningfully higher when guests are homogeneous. The binding limits in order are typically: (1) RAM, (2) one **virtiofsd process per VM** (CPU/PID/FD cost), (3) TAP/bridge scaling and nft rules, (4) host PID/FD limits, (5) vCPU oversubscription (fine for short bursty tests).
- **CPU:** vCPU oversubscription is acceptable for short-lived, mostly-idle tests; pin/limit via cgroups `cpu.max`/`cpu.weight`. Each virtiofsd and other vhost-user backend adds host threads.

### Host orchestration from Rust
- Manage a VM pool; assign each VM a cgroup v2 slice (`memory.max`, `cpu.max`, `pids.max`, `io.max`).
- Guarantee teardown on panic/kill: own the VMM child process with a Rust guard that kills the process group and removes TAP devices/bridge ports and virtiofsd sockets on `Drop`; use a reaper. Avoid fd/tap/bridge leaks by namespacing per-VM resources and cleaning in `Drop` plus a periodic sweeper. (The `processkit` crate illustrates the pattern: spawn children into "a cgroup v2 on Linux … so teardown is a kernel operation over the whole tree, not a best-effort signal to one pid.")

## Mapping the six functional requirements

1. **Console/TTY driving.** Two good options: (a) **virtio-vsock** with a small Rust PID1 agent in the guest — cleanest, fastest, no networking needed; from the host connect to the AF_UNIX socket (`/path/v.sock_PORT`) and speak your own protocol. (b) **Serial console**: capture the VMM's serial pty/stdio from Rust. (c) **SSH** via `russh` (pure-Rust, async, "based on tokio/futures"; crypto via `aws-lc-rs`/`ring`) or the `openssh` crate (wraps system ssh). For ephemeral seconds-scale tests, prefer vsock+agent; use SSH only if you need full interactive shells. `russh` is the recommended pure-Rust SSH crate (used by warpgate, Cubic VM, etc.).
2. **Three independently-permissioned shared dirs.** Run **three virtiofsd instances** (one per mount, each its own vhost-user socket and tag), with `--read-only` on (a) input data and (c) Imp binaries, and writable for (b) output. virtiofsd's `--read-only` "Prevent[s] write accesses from the guest"; combine with host mount-namespace isolation since virtiofs itself does not sandbox the shared subtree (libkrun's docs warn virtio-fs "does not provide any protection against the guest attempting to access other directories"). Cloud Hypervisor wires each with `--fs tag=...,socket=...` and requires `--memory shared=on`. Use `cache=never` for density. (Firecracker would force you to use three block devices instead.)
3. **Guest→host service access + other protocols.** Best: **virtio-vsock** for host-side HTTP/gRPC/arbitrary TCP — the test's host server listens on an AF_UNIX socket that the VMM maps to a guest vsock port; no IP routing, no firewall surprises (Cloud Hypervisor uses the Firecracker-style AF_UNIX mapping model, confirmed in docs/vsock.md). Run HTTP/gRPC over the vsock stream. Alternatively TAP + a host bridge with the host service bound to the bridge IP. For UDP or raw IP you need TAP. libkrun's TSI is an alternative if you embed libkrun.
4. **Transparent logging/filtering web proxy.** Give the guest a **TAP** interface on a host bridge; on the host, use **nftables** with a `REDIRECT`/`DNAT` rule in the prerouting hook to transparently redirect guest tcp/80,443 to a host-local transparent proxy. Use **mitmproxy** (transparent mode) for TLS interception+logging, or **Squid**, or a custom Rust proxy (e.g. built on `hyper`/`hudsucker` for MITM). TLS interception requires installing the proxy CA into the guest trust store (acceptable since you build the rootfs); log+filter at the proxy. Alternative pure-userspace path: `passt` or `gvisor-tap-vsock` (gvproxy) provide user-mode networking with built-in configurable DNS and dynamic port-forwarding and can centralize egress logging without root TAP setup; gvproxy is Apache-2.0, pure Go ("A replacement for libslirp and VPNKit, written in pure Go … brings a configurable DNS server and dynamic port forwarding").
5. **Debian-or-specialized guest.** Debian Trixie via `mkosi`/debootstrap, minimized; custom `vmlinux`; minimal or no init (Rust agent PID1). This satisfies your Debian preference while staying lean. If per-test performance becomes critical, benchmark a stripped Alpine/OpenRC or bare-`/sbin/init` guest against it.
6. **Nested virtualization (nice-to-have).** Cloud Hypervisor on KVM supports nesting where the host CPU/KVM allow it; for tests that specifically need nested VMs, run those on **QEMU/KVM** (best nested support) or Cloud Hypervisor with nested KVM enabled, as a separate VM class. Don't compromise the fast path for this.

## Recommendations

**Stage 1 — Prototype (1–2 weeks).** Stand up Cloud Hypervisor driven from Rust as a subprocess via `cloud-hypervisor-client` (pin the version). Build a minimal Debian Trixie rootfs with `mkosi`; boot a custom `vmlinux` via direct kernel boot. Implement a tiny Rust guest agent as PID1 over virtio-vsock for console/control. Wire one virtiofsd. Measure boot time and idle guest RSS on your hardware. *Benchmark to beat: <300 ms boot, <150 MiB idle guest RSS.*

**Stage 2 — Functional completeness (2–4 weeks).** Add the three permissioned virtiofs mounts (three virtiofsd, `--read-only` where required, `--memory shared=on`, `cache=never`). Add TAP + nftables `REDIRECT` → mitmproxy (or custom Rust proxy) for logged/filtered egress; install proxy CA in the rootfs. Expose host test services over vsock. Put each VM+virtiofsd in a cgroup v2 slice with `memory.max`/`cpu.max`/`pids.max`; implement `Drop`-based teardown + a sweeper.

**Stage 3 — Density & speed (ongoing).** Enable KSM (`merge_across_nodes=0`), a shared read-only base rootfs, and snapshot-clone (boot golden VM → snapshot → restore N clones with lazy/userfaultfd restore). Benchmark the concurrent-VM ceiling per RAM tier; watch virtiofsd-per-VM cost and TAP/bridge scaling.

**Thresholds that change the recommendation:**
- If you need maximum density/boot speed and can model shared dirs as block devices or over vsock → switch primary VMM to **Firecracker** (gain the ≤5 MiB-overhead spec and mature COW clones; lose virtio-fs).
- If you want true in-process embedding (no subprocess) → evaluate **libkrun** (C FFI) or **Dragonball** (Kata-coupled).
- If nested-virt tests grow beyond a niche → stand up a **QEMU/KVM** VM class for them.
- If virtiofsd-per-VM overhead dominates at scale → consider a shared/multiplexing virtiofs backend or move read-only inputs into the (shared, COW) rootfs.

## Caveats
- **Cloud Hypervisor is not embeddable as a library** — you will run it as a subprocess and talk REST/vsock. (Confirmed via the project's docs and the precedent that both Kata's `clh` driver and libvirt spawn it as a child process; no core `vmm` crate is published to crates.io for embedding.) If that subprocess boundary is unacceptable, your Rust-native in-process options are libkrun (C API) or Dragonball (Kata-coupled), or building on rust-vmm yourself.
- **All boot-time/overhead/density numbers are vendor- or third-party-reported and workload-dependent.** Firecracker's ≤5 MiB and ≤125 ms are AWS spec figures measured on M5D.metal/M6G.metal instances with the serial console disabled and a tuned kernel; Cloud Hypervisor's ~200 ms (Northflank) and virtiofs throughput vary widely. **Re-benchmark on your own hardware.**
- **virtio-fs vs 9p:** virtiofs is generally faster and more POSIX-compliant than 9p, and DAX helps a lot (Red Hat's fio numbers show virtiofs-DAX several-fold faster than 9p on some workloads), but published numbers conflict — an early Kata benchmark once showed 9p faster than virtiofs on certain read workloads, and a qemu-devel thread found 9p competitive on some writes when `msize` is tuned. 9p remains a fallback.
- **`cloud-hypervisor-client` is unofficial/auto-generated**; pin versions and consider generating your own client from the first-party OpenAPI spec for stability.
- **TLS interception** has trust and privacy implications; it works here only because you control the guest rootfs/CA. Document it.
- **Snapshot clones need uniqueness handling** (entropy/VMGenID, e.g. `MADV_WIPEONSUSPEND`) or clones may reuse RNG state/secrets (Brooker et al., arXiv 2102.12892).
- **Snapshot/restore is not guaranteed across VMM versions** for either Firecracker or Cloud Hypervisor — pin versions for a snapshot pool.
- **cgroups v2 structuring:** the cgroup-v2 "no internal processes" rule means limits may not apply cleanly under a systemd scope/service or inside a container; you may need to run the orchestrator at an appropriate point in the cgroup tree. The `cgroups-rs` crate supports v2; the older `controlgroup` crate is v1-only.
