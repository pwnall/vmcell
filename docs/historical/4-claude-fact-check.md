# Imp Testing: Ephemeral Micro-VM Integration-Testing Platform — Design Review & Fact-Check (mid-2026)

## TL;DR
- **Build on Cloud Hypervisor (v52.0, Apache-2.0/BSD-3, Rust/rust-vmm) driven as a subprocess over its REST `--api-socket`, with virtio-fs (one virtiofsd per mount) for shared dirs and a Rust vsock guest agent.** This is the architecture the three prior reports converged on, and it survives fact-checking — but several specific claims in those reports are wrong and must be corrected.
- **Three load-bearing claims are REFUTED:** (1) virtio-fs DAX is NOT available in Cloud Hypervisor (deprecated/removed); density must come from `cache=never` + KSM + ballooning, not DAX. (2) CH snapshot/restore does NOT compose with a virtio-fs rootfs (issue #6931) — you must choose a block-based rootfs for snapshot/restore OR virtio-fs for zero-copy shared dirs, not both on the same critical path. (3) `--cpu nested=on` is not the CH mechanism; nested virt is enabled on the host KVM module and passed through, not via a CH CPU flag.
- **`herolib-virt` should be avoided** as a core dependency (obscure single-author crate that merely shells out to the CH binary); use the first-party `ch-remote` + your own thin REST client (or the unofficial `cloud-hypervisor-client` 0.3.3) instead. CVE-2026-45782 is CONFIRMED real and fixed in CH v51.2/v52.0.

## Key Findings

### Recommended architecture (confirmed sound)
- **VMM: Cloud Hypervisor v52.0**, run as a child process, controlled over its REST API on a per-VM `--api-socket` (and/or the first-party `ch-remote` tool). CH is Rust, rust-vmm-based, Apache-2.0/BSD-3, actively maintained (Microsoft/Cyberus/Ant/Tencent), supports virtio-fs, vsock, nested virt, and snapshot/restore. It is NOT distributed as an embeddable library crate — subprocess + REST is the intended integration path.
- **Shared dirs: virtio-fs**, one `virtiofsd` instance per mount/tag, `--read-only` for input/binary shares, rw for the output mount; CH requires `--memory shared=on`. `virtiofsd` is the Rust rust-vmm daemon (gitlab.com/virtio-fs/virtiofsd), license Apache-2.0 AND BSD-3-Clause.
- **Console/control: a small statically-linked Rust guest agent speaking a framed protocol over virtio-vsock** (host side via an AF_UNIX socket CH exposes; CH's vsock is based on the Firecracker implementation). Serial/virtio-console wired to a per-VM log for panic capture. SSH only as a human debugging fallback.
- **Transparent egress proxy:** TAP + nftables redirect of guest egress to a host proxy. Use **TPROXY, not REDIRECT/DNAT** (see fact-check #9). The proxy can be a custom Rust proxy (hyper/rustls/hudsucker) with the CA baked into the guest trust store, enabling test doubles.
- **Guest OS:** minimal Debian Trixie rootfs assembled with `mmdebstrap`/`mkosi`, read-only erofs/squashfs base + tmpfs/overlay for writes; decouple kernel via direct kernel boot.
- **Density lever:** snapshot/restore is the biggest single lever IF you use a block rootfs; otherwise reflink/COW block overlays or virtio-fs rebind. KSM, virtio-balloon/free-page-reporting, and `cache=never` are the memory levers.

### Resolved high-priority fact-checks

**1. virtio-fs DAX in Cloud Hypervisor — REFUTED (Gemini wrong).** The current CH `docs/fs.md` states verbatim: *"Given the DAX feature is not stable yet from a daemon standpoint, it is not available in Cloud Hypervisor."* CH release notes for v24.0 record that *"The dax option from the virtio-fs support has been deprecated (#3889)."* The `dax=on,cache_size=...` syntax Gemini cited is from old/third-party documentation, not current CH. **DAX is not a real density lever today.** Density must come from `cache=never` — which the CH docs describe as *"the default when using virtiofsd with Cloud Hypervisor. This prevents from using the host page cache, reducing the overall footprint on host memory. This increases the maximum density of virtual machines that can be launched on a single host"* — plus KSM and ballooning.

**2. Snapshot/restore vs virtio-fs — REFUTED as composable (the reports' two main levers conflict).** CH issue #6931 ("Unable to restore a snapshot of vm using virtiofs root") confirms restoring a snapshot of a VM whose rootfs is virtio-fs hangs/fails. More broadly, CH rejects snapshotting VMs with vhost-user devices attached, and virtiofsd migration support only arrived in virtiofsd ≥1.11 and is still maturing (CH issue #7250 tracks migrating virtio-fs to fuse-backend-rs partly to enable snapshot/restore). **Practical consequence: snapshot/restore and virtio-fs-as-rootfs do not currently compose.** You must choose: block-based rootfs (raw/qcow2) for snapshot/restore-based fast start, OR virtio-fs for zero-copy shared dirs. You can still use virtio-fs for *data/binary shares* while booting from a block rootfs, but a snapshot taken with virtiofsd attached is not reliably restorable today — re-test on your exact CH/virtiofsd versions. (libvirt's own docs corroborate the maturity gap: *"Older versions of virtiofsd (prior to 1.11) do not support migration so operations such as migration, save/managed-save, or snapshots with memory may not [be] supported if a VM has a virtiofs filesystem connected."*)

**3. CH QCOW2 support — CONFIRMED (Gemini broadly right, others too conservative).** CH supports QCOW2 natively. v51.0 added explicit image-type specification and a `backing_files=on|off` option (default off) plus a `sparse=on|off` option; virtio-blk supports DISCARD/WRITE_ZEROES for QCOW2 and RAW (thin provisioning). v52.0 added a `QcowDiskAsync` io_uring backend (auto-selected when io_uring is available). There is a security history: v51.0 fixed a disk-image-handling vuln (GHSA-jmr4-g2hv-mjj6) and *"A new backing_files=on|off option has been added to --disk to explicitly control whether QCOW2 backing files are permitted. This defaults to off to prevent the loading of backing files entirely."* So QCOW2 thin/overlay works, but backing-file overlays are off-by-default for security and must be explicitly enabled.

**4. `herolib-virt` crate — REFUTED as a sound dependency.** It exists (docs.rs, latest **0.3.13**, license **Apache-2.0** — permissive, not copyleft, owner `despiegk`/Kristof de Spiegeleer of Incubaid–freeflowuniverse, repo github.com/herolib/herolib_rust), but it is an obscure single-author "Service Abstraction Layer" whose `cloudhv` module is a thin wrapper that launches the external `cloud-hypervisor` binary (depends on `which`, spawns processes via `nix`/`libc`, drives it over REST via `reqwest`/`hyper`/`hyperlocal`) and re-exports the real `virtiofsd` crate. It is NOT a native CH binding; the `virtiofsd` crate reports it is *"Used in 5 crates (via herolib-virt),"* indicating negligible adoption. **Avoid it as a core dependency**; write your own thin REST client or use the first-party `ch-remote` and/or the unofficial `cloud-hypervisor-client` (0.3.3, MIT OR Apache-2.0, `lpotthast`, "3,016 Downloads all time").

**5. CVE-2026-45782 — CONFIRMED.** It is a real CVE: a use-after-free in CH's `virtio-block` async I/O completion path (#8220), tracked as GHSA-f47p-p25q-83rh. The Claude report's description ("virtio-block use-after-free") is correct, but the *fix version was wrong*: it shipped in the **v51.2 point release** (May 14, 2026) and is also in **v52.0** — not "v52.0 introduced the fix" exclusively.

**6. CH nested-virt syntax — REFUTED (Gemini wrong).** There is no `--cpu nested=on` flag that "defaults to enabled on x86_64." Nested virt is enabled on the **host** by the KVM module parameter (`options kvm-intel nested=1` / `kvm-amd nested=1`), and the guest must boot a kernel with KVM built-in; CH's own `docs/iommu.md` enables it by passing `kvm-intel.nested=1` on the **guest kernel command line**. The L1 guest then gets `/dev/kvm`. Host requirements: L0 nesting enabled, hardware virt extensions, and (for clouds) a nesting-capable instance. (Per the kernel docs, on AMD once an L1 has started an L2 guest the L1 should no longer be migrated/saved — relevant if you combine nesting with snapshotting.)

**7. Current versions / recent changes (mid-2026).**
- **Cloud Hypervisor v52.0** (released ~May 14–15, 2026). Confirmed recent features: snapshot/restore treats the memory backing file as sparse (*"on snapshot the backing FD is sought with SEEK_DATA/SEEK_HOLE to skip unallocated regions, and on restore the on-disk file is read as sparse"*); AMD SEV-SNP confidential VMs on KVM via `guest_memfd`; iommufd/vfio-cdev support (Linux ≥6.6); QcowDiskAsync io_uring backend; generic vhost-user-generic device; core-scheduling option. (The reports' "userfaultfd lazy restore / vsock-reset-on-restore / virtio-fs migration" claims are NOT all confirmed in the v52.0 notes — treat as unverified.)
- **Firecracker:** still 5 emulated devices (virtio-net, virtio-block, virtio-vsock, serial console, minimal keyboard controller); still NO virtio-fs (issue #1180 open, rejected on attack-surface grounds); still no documented `/dev/kvm` passthrough (issue #1721). Confirmed unsuitable where nested virt or host-FS sharing is required.
- **Kata Containers 4.0:** runtime-rs (Rust) becoming the default; Go runtime deprecated but retained ("the Go runtime will not be removed prior to the availability of the 5.0.0 release"), with a deprecation window discussed as ~Q4 2026. Dragonball (Ant in-process Rust VMM) is a runtime-rs hypervisor option.
- **libkrun:** Rust library providing KVM/HVF process isolation; the standard variant *requires* the bundled `libkrunfw` custom kernel (so it FAILS requirement #6's "distribution kernel" goal); the EFI variant that can boot a distro kernel is macOS-only. Its security model explicitly states *"the guest and the VMM pertain to the same security context... you should think about the guest and the VMM as a single entity"* — a weaker host/guest boundary than VMM-per-VM. TSI gives netless connectivity. Not a fit for production-fidelity host-access tests.
- **rust-vmm:** monorepo consolidation (kvm/vfio/vm-virtio/vhost workspaces merging) and RISC-V support are recent themes; vm-memory has Kani formal verification and guest_memfd support; vmexec (throwaway-VM CLI) is an ecosystem consumer.

**8. Boot-time numbers — flagged as vendor/workload-dependent.** Firecracker's figures are real AWS-published numbers but measured under minimal conditions. Per Firecracker's SPECIFICATION.md: *"It takes <= 125 ms to go from receiving the Firecracker InstanceStart API call to the start of the Linux guest user-space /sbin/init process. The boot time is measured using a VM with the serial console disabled and a minimal kernel and root file system,"* and *"Firecracker's virtual machine manager threads have a memory overhead <= 5 MiB."* The marketing "up to 150 microVMs/s/host" figure is third-party-reported and benchmark-specific. CH boot is workload-dependent; the "<100 ms" (Gemini) vs "~200 ms" (Claude/Northflank) conflict is unresolved in primary sources — both are plausible under different configs. Treat all as must-re-benchmark on your kernel/rootfs.

**9. REDIRECT vs TPROXY — CONFIRMED (Claude right).** The Linux kernel docs (docs.kernel.org/networking/tproxy.html) state verbatim that REDIRECT *"actually modifies the packets to change the destination address — which might not be acceptable in certain situations. (Think of proxying UDP for example: you won't be able to find out the original destination address. Even in case of TCP getting the original destination address is racy.)"* TPROXY *"provides similar functionality without relying on NAT,"* preserves the original destination, handles UDP, and needs no conntrack. nftables `tproxy`/`socket` support exists since Linux 4.18. **For a faithful logging/filtering transparent proxy of VM egress, TPROXY is the correct primitive.**

**10. Snapshot uniqueness paper — CONFIRMED, with a terminology correction.** "Restoring Uniqueness in MicroVM Snapshots" (Brooker, Catangiu, Danilov, Graf, MacCárthaigh, Sandu), arXiv 2102.12892, Feb 4 2021, exists. The two NEW interfaces it proposes are **MADV_WIPEONSUSPEND** and **VmGenId/SysGenId** (the PDF abstract says "MADV_WIPEONSUSPEND and VmGenId"; the arXiv listing says "MADV_WIPEONSUSPEND and SysGenId"). **MADV_WIPEONFORK is a real, existing madvise flag (and the paper notes MADV_WIPEONSUSPEND is "compatible with MADV_WIPEONFORK"); MADV_WIPEONSUSPEND is the paper's PROPOSED, not upstream, flag.** Uniqueness on restore is handled via VMGenID (a 128-bit UUID surfaced via an ACPI device, originally a Hyper-V/Windows-Server-2012 mechanism) plus RNG reseeding; entropy reseed on restore is required (a real-world example: a tarpc/`getrandom()` entropy stall added ~4s to first-RPC latency until virtio-rng was trusted, after which an agent-ready boot dropped to ~0.3s).

### Additional verified claims
- **virtiofsd:** license "Apache-2.0 AND BSD-3-Clause," the Rust rust-vmm project at gitlab.com/virtio-fs/virtiofsd. `--read-only` *"prevent[s] write accesses from the guest. Note that this does not make the underlying shared directory an actual read-only mount, so e.g. the access time is still updated on accesses."* The new virtiofsd-rs Rust daemon gets the most new-feature attention.
- **Rust control crates:** `cloud-hypervisor-client` 0.3.3 (unofficial, "MIT OR Apache-2.0", OpenAPI-style REST client, "3,016 Downloads all time", `lpotthast`). `ch-remote` first-party tool with add-fs/add-net/add-vsock/add-disk/snapshot/restore/pause/resume/info/counters/shutdown subcommands.
- **Firecracker Rust SDKs:** `fctools` (rust-firecracker org) is the most actively maintained, modular, with an in-process networking backend and pluggable tokio/smol runtimes; `firecracker` crate, `firecracker-rs-sdk`, and `rustcracker` also exist.
- **QEMU from Rust:** `qapi` (arcnmx/qapi-rs, latest 0.15.0, MIT) speaks both QMP (`qmp` feature) and the qemu-guest-agent protocol (`qga` feature); the qapi family is moderately used (sibling `qapi-qmp` shows "318,115 Downloads all time").
- **`tinylabscom/mvm`:** real, active Rust CLI (mvmctl), v0.14.0 rewrite; targets Firecracker on Linux+KVM, Apple Container and libkrun on macOS; vsock-only guest agent ("NO SSH ever"), BusyBox PID 1, ext4 rootfs, dm-verity sidecar, per-service isolation (setpriv/seccomp). A strong near-reference implementation of the "vsock-only agent, no SSH" pattern.
- **`cocoonstack/cocoon`:** a real, highly-relevant 2026 entrant the prior reports missed — a lightweight MicroVM engine built on Cloud Hypervisor with OCI/cloud-image support, instant snapshot+clone via reflink, COW overlays, CNI networking with TC redirect, balloon/free-page-reporting, hugepages, Firecracker as alternative backend, explicitly designed for AI sandboxing/ephemeral dev environments. It documents exactly the constraint in fact-check #2: *"Cloud Hypervisor itself rejects snapshotting a VM that has vhost-user or VFIO devices attached, so plan accordingly."*
- **Debian Trixie (13)** is the current stable, confirmed by Debian.org: released **August 9, 2025**, shipping the **Linux kernel 6.12 LTS** series, with full support until August 9, 2028 and LTS until June 30, 2030 (13.1 point release Sep 2025). Confirmed as the right base.
- **AWS nested virtualization on non-bare-metal instances** is confirmed available (C8i/M8i/R8i-class via the `NestedVirtualization=enabled` CPU option; KVM and Hyper-V as supported L1 hypervisors) — relevant for hosting the platform in-cloud without `.metal` instances.

## Details

### Requirements-coverage assessment
1. **Host OS/arch (MANDATORY Linux x86_64):** CH fully supports Linux x86_64 and aarch64; macOS unsupported (CH has no macOS port). For macOS you'd need libkrun/Apple Container, which fail other requirements. **Verdict: met on the mandatory axis; aarch64 "good extra" met; macOS tie-breaker NOT met by CH.**
2. **Shared dirs (MANDATORY multi-dir, GREAT per-mount RO, GOOD page-cache sharing):** virtio-fs with one virtiofsd per tag gives multi-dir; `--read-only` per daemon gives per-mount RO. Page-cache sharing (the GOOD extra) historically came from DAX — which is unavailable — so this GOOD extra is **not achievable today**; `cache=never` instead minimizes guest footprint. **Verdict: MANDATORY + GREAT met; GOOD (host page-cache sharing) NOT met.**
3. **Host-served test endpoints (MANDATORY not network-exposed):** per-VM TAP on a private /30 or netns with servers bound to the gateway IP, or vsock, keeps servers host-private. Dynamic ports + per-test config are straightforward in Rust; vsock or arbitrary TCP/UDP both achievable. **Verdict: met including the GREAT/GOOD extras.**
4. **Transparent proxy (MANDATORY filter+log):** TAP + nftables TPROXY → Rust proxy. GREAT extra (Rust proxy with test doubles) achievable with hyper/rustls/hudsucker. **Verdict: met.**
5. **Debian-derivative guest:** mmdebstrap/mkosi Trixie rootfs = "good" (stripped-down Debian via supported methods). **Verdict: GOOD tier met; GREAT (full installed Debian flavor) possible if you accept the perf cost.**
6. **Distribution kernel:** Use a Debian-provided kernel image ("great") or Debian kernel source with custom options ("good"). CH can direct-boot a distro vmlinux. **Avoid the CH custom kernel for production-fidelity tests** since project-specific patches are UNACCEPTABLE. (libkrun is disqualified here — its bundled libkrunfw kernel is project-specific.)
7. **Nested virt:** CH supports it (host KVM `nested=1` + guest KVM built-in). QEMU is most-proven; crosvm partial; Firecracker NO; libkrun no. **Verdict: met with CH; peripheral passthrough is a tie-breaker only.**
8. **Programmable infra control:** CH REST API + ch-remote cover create/destroy/list, lifecycle, config (shared dirs/net/nested), and `counters`. Layer cgroup v2 (`memory.peak`, `memory.current`, `cpu.stat`, `io.stat`) for peak+avg monitoring. **Verdict: met.**
9. **Programmable artifact build:** mkosi/mmdebstrap for rootfs, a kernel build pipeline, content-addressed cache. **Verdict: met.**
10. **Programmable console (GREAT vsock Rust client+server):** the recommended vsock agent hits the top "great" tier. **Verdict: met.**

### The artifact-prep-time axis (fresh research)
The requirements doc insists VM running time *includes* per-test artifact prep. This sharpens the snapshot-vs-virtio-fs tension:
- **Block + snapshot/restore:** fastest *start* (restore in ms) but each test needs a per-test writable overlay. Use reflink/COW (XFS/Btrfs reflink, `cp --reflink`, dm-snapshot, or overlayfs) so the per-test disk fork is near-instant. CH's sparse-snapshot work (v52.0) reduces restore I/O.
- **virtio-fs:** no per-test image to copy at all — you just point a fresh virtiofsd at a new directory (or rebind), paying virtiofsd start + mount cost instead of a copy. Genuinely attractive on the artifact-prep axis.
- **The catch (fact-check #2):** virtio-fs does NOT compose with snapshot/restore. So you cannot have *both* "zero per-test image copy" (virtio-fs) *and* "ms-fast warm-snapshot start." Pick per workload tier:
  - **Short tests (seconds):** snapshot/restore from a warm "agent-ready" block snapshot + reflink overlay is likely the lowest total time.
  - **Tests needing large read-only data/binaries from host:** virtio-fs RO shares (booting from a block rootfs) avoid copying gigabytes; accept cold-ish boot, or keep a small warm block snapshot for the rootfs while mounting virtio-fs *data* shares post-restore (validate whether post-restore virtio-fs attach works on your versions — this is the key thing to test).
- **`cocoonstack/cocoon`** is a working reference for the reflink-overlay + CH snapshot/clone approach and is worth studying directly.

## Recommendations
1. **Adopt Cloud Hypervisor v52.0 as the primary VMM**, run as a subprocess controlled over REST. Pin a specific release; CH explicitly does not guarantee snapshot/restore across versions. Patch promptly (track GHSA advisories; you're already past CVE-2026-45782 if on ≥v51.2/v52.0).
2. **Do NOT depend on `herolib-virt`.** Write a thin async Rust REST client (or vendor `cloud-hypervisor-client` 0.3.3) plus a process supervisor that launches CH and one virtiofsd per share. Keep the dependency surface permissive (MIT/Apache) and auditable.
3. **Choose your fast-path per test tier rather than assuming one design.** Implement BOTH: (a) a block-rootfs warm-snapshot path (reflink overlay) for the seconds-tier majority, and (b) a virtio-fs RO-share path (block rootfs boot) for data-heavy tests. Benchmark both on your real kernel/rootfs before committing; the snapshot+virtio-fs incompatibility (#6931) is the single biggest architectural fork.
4. **Use TPROXY (not REDIRECT) for the egress proxy**, with a Rust proxy (hyper/rustls/hudsucker) and a baked-in CA, so you get faithful destination preservation, UDP support, and test doubles.
5. **Guest: Debian Trixie via mmdebstrap/mkosi, distro kernel image (6.12 LTS), no project-specific kernel patches.** Build KVM into the guest kernel for nested virt. Trust virtio-rng (reseed on restore) to avoid `getrandom()` stalls.
6. **Monitoring: one cgroup v2 slice per CH process**; read `memory.peak`/`memory.current`/`cpu.stat`/`io.stat`, layered with CH `counters`. Density levers: `cache=never`, KSM (with `merge_across_nodes=0` on NUMA — the kernel KSM admin guide states *"When set to 0, ksm merges only pages which physically reside in the memory area of same NUMA node. That brings lower latency to access of shared pages,"* and Red Hat recommends this when KSM is in use), and virtio-balloon/free-page-reporting. Budget for KSM's CPU cost: the OpenVZ/Virtuozzo wiki notes *"KSM has a 5-10% CPU overhead depending on its configuration."* Treat 128–256 MiB/guest as a must-re-benchmark planning figure.
7. **Console/control: ship the Rust vsock guest-agent** (framed protocol, tokio-vsock/AF_UNIX host side), serial→per-VM log for panics, SSH only for human debugging. Study `tinylabscom/mvm` and `cocoonstack/cocoon` as reference implementations.

**Benchmarks/thresholds that change the recommendation:** If on your versions post-restore virtio-fs *data* shares attach reliably, prefer the warm-snapshot + virtio-fs-data hybrid universally. If virtiofsd start cost dominates for many small shares, prefer block+reflink. If you ever need macOS hosting as more than a tie-breaker, re-evaluate libkrun/Apple Container (accepting the weaker single-security-context model). If Firecracker adds virtio-fs or `/dev/kvm` passthrough (watch issues #1180/#1721), reconsider it for the density-only, no-nesting tier.

## Caveats
- **Snapshot/restore + virtio-fs incompatibility** is the highest-risk item; it directly contradicts the prior reports' recommendation to use both as the main levers. Validate empirically on pinned versions.
- **DAX is gone** — any density plan that assumed shared host-page mapping via DAX is invalid.
- **Boot-time and density numbers are vendor/workload-dependent** and unreconciled across sources; all require local benchmarking. The "150 microVMs/s/host" figure in particular is benchmark-specific marketing, not a guarantee.
- **CH macOS support does not exist;** the nice-to-have macOS tier forces a different (weaker-isolation) stack.
- **Some v52.0 feature claims in the prior reports (userfaultfd lazy restore, vsock-reset-on-restore, virtio-fs migration) are NOT all confirmed** in the release notes I verified; sparse snapshot, SEV-SNP, iommufd, and QcowDiskAsync are confirmed. Treat the unconfirmed ones as unverified.
- **`herolib-virt` exact download count could not be verified** (likely negligible); the recommendation to avoid it stands on its single-author, shell-out nature regardless.
- **The CH "<100 ms vs ~200 ms" boot conflict is genuinely unresolved** in primary sources; do not quote either number as authoritative.
