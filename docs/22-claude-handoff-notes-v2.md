## 1. Orientation

Imp Testing is a Rust library + CLI that runs each integration test for the **Imp** agentic harness inside its own micro-VM (structural isolation, hermetic state, production fidelity). Victor is building Imp; this project tests it.

**The four artifacts and how they relate — read in this order:**

1. **Requirements** (`requirements.md`) — the contract, written in tiers. A **10-item micro-VM feature checklist** (Linux/x86_64; multiple shared dirs with read-only perms + host page-cache sharing; host HTTP servers not exposed to the LAN, per-test, dynamic ports; a transparent web proxy with Rust test doubles; a Debian-flavored userspace; a Debian-flavored kernel — custom-compiled OK, project-specific patches *not* OK; nested virt; programmable VM management/lifecycle/config + resource monitoring; programmable staged artifact build; programmable console — vsock+Rust preferred over SSH), plus **non-functional attributes** (per-test running time *including artifact prep*; RAM/density as the parallelism limit; driven entirely from Rust; permissive licensing for linked crates, copyleft tolerated only for external binaries), **source-code requirements** (one 2024-edition package, all-in-one lib + a CLI bin wrapping it, one integration test per requirement/op, clippy/rustfmt, unit tests), and **artifact-production requirements** (staged → pinned → deterministic → cacheable → reset-to-stage → record/replay → signing-chain-verify). Most checklist items are tiered mandatory→nice-to-have, so **non-mandatory features are tradeable for performance** — that tiering is *why* losing DAX page-cache sharing is acceptable. Design **§6** is the formal requirement→design mapping (its internal requirement numbering is its own; refer to requirements by name to avoid cross-artifact number drift).
2. **Design doc** (`18-claude-design-v10.md`) — **the single source of truth for what to build.** Self-contained: architecture, the `Vmm` trait, the agent protocol, the artifact pipeline, the kernel config (§7), the testing strategy and quality gates (§12, incl. the §12.8 capability test-runner), benchmarking (§13), and **§14 = implementation feedback** (validated / invalidated / refinements). Start at §14.
3. **Implementation notes** — field notes from agents building against the design. **CRITICAL: these are CHRONOLOGICAL and partly self-superseding.** Early entries ("Exp 4 / OCI skipped," "mmdebstrap on the host," "mkfs.erofs used," "30 s exec timeout") were written *before* later entries in the same file that reverse them ("OCI + in-VM mmdebstrap implemented," "am-fs-erofs adopted," "timeout → 600 s"). **Read the whole file before acting, and do not regress the design to an early-entry state.** The design (v10) already reflects the latest state; §14.4 lists the superseded notes explicitly.
4. **These handoff notes** — the meta-layer.

**Naming convention.** Inputs are numbered files in rough chronological order (`15-handoff`, `16-design-v8`, `17-design-v9`, `18-design-v10`, …). On a substantive design revision, **the file number and the version increment together** (17/v9 → 18/v10). The design carries inline **(observed)** / **(observed, v10)** call-outs wherever a finding came from an actual implementation pass — preserve this so the empirical parts stay distinguishable from the reasoned ones.

**Where things stand.** The architecture has survived **three implementation passes** + a dependency study + a code review without being overturned. The third pass is the most complete: it built the Firecracker backend, the `imp-test-runner` capability runner, both rootfs sources (OCI + in-VM mmdebstrap), rootless cgroup-v2 delegation, and the full integration suite. **There is now real code** (unlike the v8-era handoff, which had only a `Cargo.toml` sketch). The design and the implementation now have a small, *tracked* **gap**: a few places where the build deviated from or invalidated the spec (all in §14) — some deviations accepted into the design (REDIRECT), some pending reconciliation back to spec (the agent's netlink path). The current job is mostly: drive the open validations, reconcile the deviations, and keep design and reality converged.

## 2. The decision ledger — settled, don't reopen without new evidence

Load-bearing, each chosen for a reason. A vague sense there might be a cleaner way is not grounds to reopen; new evidence is. Full rationale lives in the cited design sections.

- **VMM = Cloud Hypervisor, subprocess over its REST socket** (not embedded — no embeddable crate; only option doing virtio-fs + vsock + nesting + snapshot *simultaneously*). Firecracker = optional dense backend; QEMU = fallback nester. The `Vmm`/`VmInstance` trait is the boundary, and **`capabilities()` on it is load-bearing** — the third pass independently found it necessary and added it (§5.2). Backends advertise what they support; the test/bench matrix skips the rest.
- **Rootfs = erofs, read-only, shared across all VMs with no per-VM copy; tmpfs overlay for writes** (§3.2/§7). Killed the ext4-RO-journal panic and concurrent-mount corruption, composes with snapshot (a plain block device, not vhost-user), recovers page-cache density.
- **Rootfs source = BOTH, selectable. (This REVERSES the v8 "mmdebstrap, NOT OCI" entry — v9 resolved it by supporting both.)** Default = host-native, mostly-Rust **OCI pull** (`oci-client`, pin by `sha256` digest, in-memory whiteout application → merged tar). Full-apt = **`mmdebstrap` relocated INTO a builder micro-VM** (boots an OCI-built builder rootfs, runs apt/mmdebstrap in-guest, returns a tar), which moves apt/gpg/dash/mmdebstrap OFF the host. Honest trade: OCI default = digest *integrity*, not *provenance* unless cosign is added; the in-VM mmdebstrap source keeps the full apt signing chain. Bootstrap chain is acyclic (OCI needs no VM). (§7, §10 Exp 4 — graduated.)
- **Rootfs build = `am-fs-erofs`, in-memory tar→erofs** (graduated, §10 Exp 3); `mkfs.erofs` binary fallback. Runs unprivileged (no device nodes / root uids on the host).
- **Control plane = vsock + a Rust guest agent as PID 1**, postcard length-delimited framing, accept-in-a-loop, reconnect-after-restore, NO SSH (debugging fallback only). The hybrid-vsock handshake is shared by CH and Firecracker (validated — FC needed no protocol change).
- **Agent linking = dynamic-glibc default, static-musl optional** (the rootfs ships `libc6`; `musl-tools` isn't installable unprivileged in some CI).
- **Networking = two modes behind `NetConfig`.** Privileged: netns + tap + `/30` + egress steering. Rootless: in-process **smoltcp** + `vhost-user-backend` NAT (graduated; now a *default* feature). **passt is dead** — CH-incompatible (its C seccomp filter drops the `accept4` CH's vhost-user connection needs, no opt-out). Don't propose passt.
- **Egress steering: as-built uses `iptables REDIRECT` + `SO_ORIGINAL_DST`; `nft TPROXY` is the documented upgrade** (not a bug — v10 *corrected* the earlier overclaim that REDIRECT "can't preserve the destination"; it can, for IPv4 TCP). TPROXY's real edge is UDP/QUIC, source preservation, and no conntrack dependency across the netns boundary. nft rules applied via the **`nft` binary**, not a crate (`rustables` is GPLv3; Exp 2 rejected).
- **Privileged tests run via `imp-test-runner`** (the capability runner, §12.8), NOT `sudo -E`: file-caps (or setuid) grant only `CAP_NET_ADMIN`+`CAP_SYS_ADMIN`, drop the bounding set, raise the ambient set, drop to the dev uid, `execve` the test — so artifacts stay dev-owned and the test holds two caps, not full root. Built and validated. `sudo -E`/a root job is the CI-only fallback. KVM access is the `kvm` group, not a capability.
- **Snapshot/restore sequencing is exact** (observed against CH): snapshot = pause → snapshot → (resume); restore = `--restore` → `resume`, **never** create/boot (CH returns 500 "VM is already created"). On restore: rotate identity (CID/MAC/IP), reseed entropy, **resync the clock host-driven** (the guest can't — hwclock restores the OLD time), and **reconnect the severed vsock** (CH re-creates the host socket; the agent survives the EOF and re-accepts).
- **Source layout = one package, 2024 edition**: lib + CLI bin + lean feature-gated guest-agent bin + the lean `imp-test-runner` bin + a `bench-vm` bin. `cargo-deny` is the license gate **and the source of truth on licensing** (not hand-written labels).

## 3. Open threads — what to drive next (roughly prioritized)

1. **Firecracker snapshot is the biggest open item.** FC can't snapshot with `--enable-pci`, which the PCI-only guest kernel currently forces → FC reports `snapshot_restore: false` and the suite skips it (graceful, honest). **Decision needed:** (a) validate the `CONFIG_VIRTIO_MMIO=y` kernel path (added to §7) + run FC in MMIO mode to regain snapshot — confirm one `vmlinux` boots clean over both PCI (CH) and MMIO (FC) — or (b) formally accept FC-as-no-snapshot. Gates whether §13.2's cross-backend lazy-restore comparison can ever run. (§14.2 #1.)
2. **`ip=` agent-free re-test — preserve the zero-netlink invariant.** The third pass found `eth0` unconfigured and put `ip link/addr/route` BACK into the agent, blaming "no initramfs" — almost certainly a misdiagnosis (IP-PNP is kernel-level; the real cause was `net-rootless` compiled out → no virtio-net device). Re-test with the device present + `CONFIG_IP_PNP=y`/`CONFIG_VIRTIO_NET=y` built in; if `ip=` configures `eth0`, **remove the agent bring-up** — the §12.4 Netlink-fake test asserts zero netlink in PID 1. (§14.2 #2.)
3. **The snapshot↔virtio-fs fork (highest-risk *unvalidated* unknown, carried from v8).** The erofs-block rootfs snapshots cleanly; whether virtio-fs *data* shares can be re-attached to a snapshotted VM on the pinned CH/virtiofsd is still unvalidated (attaching virtiofsd, a vhost-user device, is what makes a VM snapshot-ineligible). Build both paths (virtiofsd data shares vs extra erofs/block data images), pick per tier from measurement. Gates the M8↔M3 interaction.
4. **Rootless memory limits are best-effort.** The `memory` controller may be undelegated even on Ubuntu 26.04 (`memory.high` → "Operation not supported"). The design degrades (read `memory.current`/`peak` from sysfs, surface `limits_enforced: bool`); finalize that and decide whether hard enforcement requires the privileged path or a confirmed `systemd-run --user` delegation. (§14.2 #3.)
5. **No performance numbers are validated.** §13 is the suite that settles the §3 contested facts (boot <100 ms vs ~200 ms; density; restore latency; OCI-vs-mmdebstrap hot-path parity). Don't quote any as fact until §13 has run on the pinned substrate. The privileged→rootless *default* migration is explicitly gated on the §13.5 datapath comparison.
6. **`loom` concurrency tests still deferred** (CID/VMID allocator, proxy state). Opt-in per §12.3; the standalone `Cargo.toml`'s commented `loom` line is where to land it.
7. **`am-fs-erofs` license still wants a `cargo-deny` pass.** Adopted and working, but obscure enough that a web search couldn't confirm its license — gate it. `mkfs.erofs` is the fallback if it's copyleft/unmaintained.
8. **`fuse-backend-rs` (Exp 1) not concluded.** In-process virtio-fs behind `experiment-fuse`; does NOT fix the snapshot↔virtio-fs fork for an external CH (CH still sees a vhost-user device). virtiofsd remains the fallback.
9. **Two CH-version-pinned claims to re-check on the pin:** DAX availability (treated unavailable per the better-sourced fact-check — re-check `docs/fs.md`) and userfaultfd lazy restore in the pinned CH.

## 4. Landmines — things that have actually burned us

*New (v9/v10) first, then durable.*

- **Don't re-assert that Firecracker snapshots.** It doesn't, under the PCI mode this kernel needs (§14.2 #1). The capability machinery handles this correctly; don't "fix" the skip by claiming FC supports snapshot.
- **The implementation notes are chronological and self-superseding** (see §1.3). The single most likely way to damage the design is to act on an early, later-reversed entry (host mmdebstrap, OCI skipped, mkfs.erofs, 30 s timeout). Read the whole file; §14.4 lists the stale ones.
- **vsock handshake: read the `OK <port>\n` line with EXACT 1-byte reads, never a `BufReader`** — a buffered reader pre-fetches the first framed payload, which is then silently dropped, manifesting as a mystery connection timeout (§5.2).
- **smoltcp NAT has four non-obvious invariants** (§5.3): host MAC pinned to `02:00:00:00:00:fe` (a source-MAC collision with the guest silently drops broadcasts); iterate the virtio RX descriptor chain ONLY when packets are queued (iterating while empty advances `avail_idx` and permanently wedges the link); `enable_notification()` on TX inside `handle_event`; pool ≈16 sockets per forwarded port (1/port exhausts under HTTP keep-alive).
- **cgroup v2 "no internal processes" rule** (§5.3): the runner is itself an internal process, so per-VM cgroups must be created as **siblings** (move the runner to a `…/supervisor` leaf), not children; write the PID directly to `cgroup.procs` (`cgroups-rs add_task` errors/hangs on deep nesting); and the `memory` controller may simply not be delegated.
- **Clock resync must be host-driven** — `hwclock --hctosys` on a restored VM sets the clock *backwards* to snapshot time (§7); the host injects `now()` over the agent after reconnect.
- **VMID/CID allocators must be process-global** (one shared instance), or parallel `cargo test` hands out identical IDs → temp-dir/socket collisions. The vmid→IP-octet map must be `(n % 254)+1`, which caps ~254 concurrent VMs on one `/16` — widen the octet beyond that (§5.3).
- **Kernel: everything the guest needs at boot must be built-in (`=y`), because there is NO initramfs** — virtio transport(s), virtio-net, IP-PNP, erofs, vsock. A `=m` for any boot-path driver silently breaks boot or `ip=`. Build BOTH virtio-pci (CH) and virtio-mmio (the FC snapshot path) (§7).
- **Crate licenses: verify, never trust the label.** `rustables` was presented as MIT/Apache; it's GPL-3.0. `cargo-deny` is the gate. Apply the same suspicion to every obscure crate (`am-fs-erofs` still pending).
- **The Gemini-optimism pattern.** Gemini reports recommend obscure single-author crates, overclaim maturity (erofs writers, DAX), and underweight implementation cost (smoltcp framed as "easy" — it had four invariants). Cross-check Gemini claims against primary sources before folding them in.
- **"Most recent ≠ most correct."** A *later* Gemini fact-check re-introduced the DAX error an *earlier* Claude fact-check had already refuted with a verbatim source quote. Defer to the better-sourced claim and flag the conflict, not to recency.
- **Subprocess supervision is silently fatal if sloppy.** A misconfigured `virtiofsd` exits immediately, but socket-polling alone hangs CH forever — surface the child's exit/stderr AND bound the socket-wait with a timeout. (The flag is `--readonly`, not `--read-only`.)
- **Don't reverse a settled/graduated decision to chase tidiness.** If a substitution was rejected (pure-Rust nftables) or a tool kept (mmdebstrap), the reason is recorded; re-proposing it without new evidence wastes Victor's time.

## 5. How to maintain the artifacts

- **The design doc is living, edited via `str_replace`.** Keep section numbers stable — cross-references use `§N` throughout (there are ~13 back-refs to §14 alone); renumbering breaks them. Grep for references before moving a section. **Verify code-fence balance (count of ``` must stay even) after edits.**
- **TWO copies of the `Cargo.toml` drift:** the standalone artifact and the embedded §5.5 copy. They are currently out of sync — **the standalone copy still needs the v9/v10 additions**: `oci-client` (with `default-features=false, features=["rustls-tls"]`), the `criterion` dev-dep + `[[bench]] micro` + `[[bin]] bench-vm`, the `imp-test-runner` bin + `test-runner` feature + `capctl` dep, and confirm `proptest = "1"` plus the commented `loom` line. When you change one, change both and re-verify against §5.5.
- **`deny.toml`** (the concrete form of the license gate) may still not exist as a standalone file — low-effort, high-value to create; mirror the §5.4 allow-list (MIT / Apache-2.0 / BSD-3 / ISC / Zlib) and the advisory DB.
- **When new inputs arrive** (research or implementation notes): assess critically *first* — verify the load-bearing checkable facts (crate licenses/versions especially) with a search when the stakes are real — *then* fold conclusions into the design **body** (not just an appendix), *then* update these notes. Classify each experiment graduated / rejected / postponed / underway, and reflect adopted ones in the main body. Mark empirical findings `(observed)`.
- **The design vs. the implementation will keep diverging — that's the loop working, not a failure.** Track deviations in §14 and decide *per deviation*: accept it into the design (e.g., REDIRECT) or reconcile the implementation back to spec (e.g., remove the agent's netlink path). Don't let the two silently drift.
