# Implementation Notes

## V10 Design Revision Updates
- **Firecracker MMIO and Snapshotting**: Following the v10 design revision, the guest kernel was configured with `CONFIG_VIRTIO_MMIO=y`, and Firecracker now runs in its native MMIO mode instead of PCI mode. As a result, Firecracker's snapshot/restore capability is fully supported and enabled in `capabilities()`.
- **Agent-free Networking**: We confirmed that `ip=` kernel parameters correctly configure the network via IP-PNP when the network device is present (`net-rootless` feature). We removed the manual network bring-up from the test suite and the guest agent, preserving the zero-netlink invariant for PID 1.
- **Vestigial Shell Check**: We removed the vestigial `/bin/sh` to `bash` symlink check from the host builder (`imp-testing.rs`), as `mmdebstrap` now runs inside the builder VM, and any shell quirks are isolated to the builder rootfs.

## Rootless Networking and Passt (`vhost-user` issue)
- We attempted to use `passt` for rootless networking with `cloud-hypervisor` via `--net vhost_user=true`.
- However, `passt` fundamentally crashes during the `vhost-user` socket connection phase. A system call trace (`strace`) reveals that `passt`'s strict `seccomp` sandbox drops the `accept4` syscall (used to accept the connection from `cloud-hypervisor`) with `EACCES` (Permission denied). This immediately cascades into `epoll` errors (`Failed to add fd to epoll: Bad file descriptor`).
- Since `passt` is written in C and does not provide an option to disable its seccomp profile, it is incompatible with `cloud-hypervisor` in this setup.
- **Resolution:** To achieve rootless networking, we successfully implemented **Experiment 5** from the design doc: a pure-Rust userspace network NAT using the `vhost-user-backend` and `smoltcp` crates.
- **Smoltcp Implementation Details:**
  - **MAC Collisions:** `smoltcp` will silently drop packets if the Ethernet destination MAC is Broadcast but the Source MAC happens to equal the `smoltcp` interface's configured MAC. To avoid a collision with the guest's MAC (which is derived from the `vmid`), we statically assign the host's `smoltcp` MAC to `02:00:00:00:00:fe`.
  - **RX Queue Iteration:** When polling `smoltcp` in the background thread, it processes packets and pushes replies (like ARP and SYN-ACKs) into an `rx_queue`. The virtio RX queue descriptor chain must *only* be iterated if we actually have packets in the `rx_queue` ready to send to the guest. Iterating `vring_state.get_queue_mut().iter()` automatically consumes and advances the `avail_idx` pointer; doing this when `rx_queue` is empty effectively drops all of the guest's provided RX buffers, permanently breaking the connection.
  - **Notifications:** We must call `vring_state.enable_notification()` for the `TX` queue inside the `vhost-user-backend` `handle_event` loop so the guest agent knows when to kick the eventfd for subsequent packets.
- With these fixes, the integration tests `test_egress_proxy.rs` and `test_host_endpoint.rs` now run successfully without requiring `sudo` or TAP interfaces.
## Rootless Cgroup v2 Delegation
- To enforce memory and CPU limits unprivileged, we must nest the per-VM cgroups inside the test runner's current systemd delegated cgroup slice.
- `cgroups-rs`'s `CgroupBuilder` defaults to creating cgroups at the root (`/sys/fs/cgroup/imp-vm-XXX`), which fails with `Permission denied` without root.
- **Resolution:** We updated the `orchestrator` to read `/proc/self/cgroup` and dynamically construct a nested path for the VM's cgroup.
- **Cgroup v2 Constraints:** The kernel enforces a "no internal processes" rule: a cgroup can either have processes or distribute resources to children (by enabling controllers in `cgroup.subtree_control`), but not both. Because the test runner (`cargo test`) itself constitutes an internal process within its parent scope, we cannot easily enable `memory` or `cpu` controllers for child cgroups created directly underneath it. To bypass this for testing environments where we manually moved the agent to a `supervisor` sibling, we strip the `/supervisor` suffix from the path when creating the VM cgroup, ensuring it gets created as a sibling with full controller access.
- **cgroups-rs Limitations:** `cgroups-rs`'s `Cgroup::load().add_task()` throws a `CgroupMode` error when attempting to add processes to deeply nested unprivileged cgroups. To avoid this and a subsequent test-hanging panic, we directly write the PID via `std::fs::write(cgroup.procs)`.
- **Missing Memory Delegations (Ubuntu 26.04):** Even on modern systems with fairly new software (e.g., Ubuntu 26.04), we observed that the sandbox or test environment might not fully delegate the `memory` controller to unprivileged users or test runners by default. As a result, attempts to set `memory.high` or similar limits within the delegated nested cgroups can fail with "Operation not supported" or "No such file or directory". This limitation is an environment issue rather than an implementation flaw, and the codebase correctly attempts to configure the delegated cgroup as specified in the architecture design.

## Subprocess and virtiofsd Fixes
- When falling back to the external `virtiofsd` binary (when `experiment-fuse` is disabled), passing `--read-only` crashes the subprocess (`error: unexpected argument '--read-only' found. tip: a similar argument exists: '--readonly'`).
- Since `std::process::Command` errors aren't surfaced automatically if the parent process merely polls for the socket's existence, `cloud-hypervisor` hangs indefinitely waiting for `virtiofsd`'s vhost-user socket.
- **Resolution:** We corrected the flag to `--readonly` and added robust timeout error handling when waiting for the socket file to exist.

## Snapshot and Restore
- `cloud-hypervisor`'s `/api/v1/vm.snapshot` API requires the VM to be paused first using `/api/v1/vm.pause`. Resuming after snapshot with `/api/v1/vm.resume` is not strictly necessary if the VM is immediately shut down, but is generally good practice.
- When a VM is restored from a snapshot (via `--restore source_url=file:///...`), the guest's state is fully resumed. The VM does NOT require an explicit `/api/v1/vm.create` or `/api/v1/vm.boot` API call. Trying to boot a restored VM returns a `500 VM is already created` error from `cloud-hypervisor`.
- Instead, for restored VMs, we just call `/api/v1/vm.resume` to ensure execution continues.

## Guest Agent Vsock Connection
- When the VM is snapshotted and restored, the original vsock connection (between the host test runner and the guest agent) is severed because the host-side `vhost-vsock` device is re-created with a new socket.
- As a result, the guest agent receives an EOF on the vsock stream.
- The guest agent's connection handling loop must properly detect this EOF and exit the `handle_connection` loop so that it can `accept` a new connection from the test runner after the restore completes.
- We switched the guest agent serialization to use `postcard` consistently with the host, ensuring length-delimited framing works correctly.

## Dependencies
- `mmdebstrap` uses `dash` by default on Ubuntu, but `dash` fails. Setting `SHELL=/bin/bash` in the environment works around this limitation.
- It's also important to ensure `/bin/sh` points to `/bin/bash` when using `mmdebstrap` directly without `SHELL` environment overrides. The `imp-testing build` script explicitly checks for this symlink and halts execution if it's not configured correctly.

## Rootfs and EROFS
- `mkfs.erofs` is used to build the root filesystem. The kernel needs `CONFIG_EROFS_FS=y` built-in, otherwise it panics when attempting to mount the rootfs.
- If `imp-guest-agent` is dynamically linked in the EROFS image, it will work because `mmdebstrap` via `minbase` installs `libc6`. Attempting to statically link against `musl` requires `musl-tools` installed on the host, which is not available without root on some test environments.

## Architectural Experiments
- **Experiment 2 (Pure-Rust Nftables):** Skipped. The goal was to replace the `iptables` / `nft` CLI invocations with a pure-Rust implementation using permissive crates. `jip-nftables` was evaluated but only provides read capabilities. `rustables` provides write capabilities but is GPLv3 licensed, disqualifying it. Writing complex netlink payloads from scratch for a tiny ruleset was deemed unjustified.
- **Experiment 3 (Pure-Rust EROFS Build):** Successfully implemented. Replaced the `mkfs.erofs` shell-out with the `am-fs-erofs` crate. The `mmdebstrap` output is streamed directly into a custom `tar_to_erofs` in-memory parser, which converts the tar entries into an `am-fs-erofs` `Node` tree and compiles the image. This bypasses the host filesystem entirely, avoiding permission issues with creating device nodes or setting root uids as a non-root user.
- **Experiment 4 (OCI-image rootfs):** Skipped. Postponed to preserve the `apt` signing chain verification provided by Debian's `mmdebstrap`.

## Design Deviations and Quality Improvements
- **CidAllocator:** Originally, the CID for `vhost-vsock` was hardcoded to `3`. We have introduced a thread-safe `CidAllocator` in `vmm/mod.rs` that dynamically increments and allocates guest CIDs, resolving port conflicts and complying with the design requirement to support concurrent testing.
- **Pause/Resume support:** To ensure safety across checkpoints, we added explicit `pause()` and `resume()` lifecycle hooks to the `VmInstance` trait and correctly wired them to the Cloud Hypervisor REST API.
- **Documentation and Rust API Guidelines:** `#![deny(missing_docs)]` and `#![deny(clippy::missing_errors_doc)]` were added to the crate root to ensure comprehensive documentation. We documented all structs, traits, properties, and methods in the framework, adhering strictly to the Rust API Guidelines.
- **Iptables REDIRECT instead of Nftables TPROXY:** The design originally called for `nft` TPROXY to intercept egress traffic transparently. However, `iptables` REDIRECT rule (`-j REDIRECT --to-ports`) is used instead for simplicity as it relies on fewer kernel dependencies and is easier to invoke directly from the test orchestrator.
- **Guest Agent Networking Setup:** We have successfully migrated networking configuration entirely out of the guest agent. The guest agent now relies entirely on the Linux kernel's `CONFIG_IP_PNP=y` feature and `ip=` bootline arguments to automatically configure the network interface (`eth0`) and routes upon boot.
- **HTTPS MITM Proxy Support:** We replaced the basic `hyper` proxy with `hudsucker` to support full HTTPS interception. A dynamic CA is generated at runtime via `rcgen` and automatically injected into the root filesystem via `mmdebstrap` hooks.
  - *Difficulty (CONNECT Interception):* When intercepting HTTPS, `hudsucker` passes the initial `CONNECT` request to the `HttpHandler`. If a test double blindly matches the target host and returns a response for the `CONNECT` request, it breaks the proxy tunnel protocol, resulting in `unexpected eof while reading` TLS errors. We resolved this by explicitly ignoring `hyper::Method::CONNECT` in our test double matchers.
  - *Difficulty (API Changes):* Integrating `hudsucker` v0.23 and `rcgen` v0.13 required updating to modern API patterns, such as the strict ordering of `ProxyBuilder` (`with_ca` before `with_rustls_client`), passing graceful shutdown futures, and using `params.self_signed(&key_pair)` for certificates.

## Code Review Bug Findings & Fixes
- **Unsafe setns Syscalls:** The raw `libc::setns` syscalls in the test orchestrator lacked documentation and safety comments. These have been hardened with `Result` mappings to propagate errors gracefully, avoiding unexpected thread crashes.
- **Guest Agent `SIGTERM` Ignoring:** The `imp-guest-agent` registered a `SIGTERM` handler flag but immediately exited its main loop instead of gracefully waiting. This was fixed by utilizing `term.load()` properly inside a long-running event loop.
- **cgroups-rs Panic on Missing Controllers:** In environments where `memory` controllers are not delegated to the test runner slice, calling `m.memory_stat()` via `cgroups-rs` panicked (as `memory.high` is absent). This was bypassed by reading `memory.current` and `memory.peak` from `sysfs` manually to maintain robustness across constrained environments.
- **VMID Generation Collision:** `TestVm::vmid` generation originally utilized a raw atomic addition combined with PID multiplication, which occasionally produced VMIDs > 255. Because these IDs were substituted into IPv4 octets (`10.200.<vmid>.1`), it generated invalid IPs. This was fixed by wrapping the atomic counter specifically within `(c % 254) + 1`.
- **Guest Agent `EINTR` Race Condition:** The agent's `exec` handler was occasionally dropping stdout/stderr chunks due to a subtle race condition when the `std::process::Child` exited. `SIGCHLD` signals interrupted the blocking `read` syscalls on the pipe, returning `EINTR`, which our loop mistakenly treated as a fatal read error. We resolved this by explicitly handling `ErrorKind::Interrupted` and tightly joining the output reader threads before signaling completion.

## Code Review Implementation Difficulties
- **Cloud Hypervisor Clock Resync on Restore:** When a VM is restored from a snapshot, Cloud Hypervisor restores the RTC to the exact time of the snapshot. Because the `snapshot_restore` test runs with networking disabled (precluding NTP), `hwclock --hctosys` inside the guest simply sets the system clock back to the old snapshotted time rather than the host's current time. To successfully assert a clock resync, we had to manually fetch the host's `SystemTime::now()` and inject it via `date -s` over the guest agent connection.
- **Silent Network Omission in Rootless Mode**: In `egress_proxy.rs`, the test requested `NetConfig::Rootless`. However, because the `net-rootless` Cargo feature was not enabled by default, the `vhost-user` socket setup was conditionally compiled out, causing the VM to boot without a network interface (`eth0`). We fixed this by adding `net-rootless` to the default features. With the device present, the kernel's built-in IP-PNP (`CONFIG_IP_PNP=y`) correctly parses the `ip=` bootline parameter, allowing us to remove all manual network initialization (`ip link`, `ip addr`, etc.) from the test suite and guest agent, preserving the zero-netlink invariant for PID 1.
- **SmolTCP Socket Exhaustion:** While testing transparent proxy interception in `egress_proxy.rs`, the first `curl` request succeeded but left the connection intact (HTTP Keep-Alive). The subsequent `curl` request for the blocked domain was rejected with `Connection refused`. We discovered that `src/net/smoltcp.rs` was rigidly allocating only 1 `TcpSocket` per forwarded port, immediately exhausting the socket pool. We resolved this by refactoring the networking backend to allocate 16 `TcpSocket` instances per forwarded port, ensuring it handles multiple sequential connections properly.

## Remaining Divergences from the Design
- **Concurrency Testing (`loom`):** The design document and code review both strongly recommended introducing `loom` for deep concurrency testing (particularly for `CidAllocator` and proxy state). This was skipped in the current phase to focus on addressing critical correctness bugs and stabilizing the standard integration test suite first.
- **Rootless Networking Default:** Although the `net-rootless` (`smoltcp`) feature is complete and working, `net-privileged` (TAP/TUN with `sudo`) is still frequently relied upon in the core integration test suite. Complete deprecation of privileged tests in favor of rootless `vhost-user-backend` is pending further network performance validation.

## Recent Refactoring Findings
During the recent code review feedback implementation, a few notable challenges were encountered and resolved:
- **`hyper` 1.0 IO Traits:** Replacing the hand-rolled HTTP parser required integrating `hyper` and handling its stricter IO constraints. A bare `tokio::net::UnixStream` cannot be passed directly to `hyper::client::conn::http1::handshake`; it must first be wrapped in a `hyper_util::rt::TokioIo` shim.
- **`hyper::Response` Consumption:** During the HTTP parser refactor, accessing `res.status()` after reading the body caused a borrow checker error because `res.into_body()` inherently consumes and moves the response object. The status code had to be cached prior to body consumption.
- **`TestVm` Connection Re-use and Borrowing:** Caching the `AgentClient` vsock connection as an `Option<AgentClient>` inside `TestVm` and returning a `&mut AgentClient` introduced a strict mutable borrow against the entire `TestVm` instance. In integration tests like `egress_proxy.rs`, this prevented the test from accessing `vm.vmid()` and `vm.proxy()` later in the flow. We resolved this by querying and caching immutable properties into local variables *before* connecting the agent.
- **Pervasive Allocator Injection:** Updating `TestVm::start` to accept an injected `Arc<VmidAllocator>` surfaced the fact that the integration test suite heavily relied on the implicit static allocator. This required pervasive updates across all test modules to manually instantiate and pass an `Arc<VmidAllocator>` context.
- **Strict Clippy Escalation:** Enabling `#![deny(clippy::unwrap_used)]` and `#![deny(clippy::missing_errors_doc)]` necessitated replacing numerous instances of `.unwrap()` with proper `ok_or_else` mappings, particularly in `artifact/rootfs.rs` and `artifact/tar2erofs.rs`.
- **`#[non_exhaustive]` Struct Expressions in Tests:** While writing `proptest` cases for `Message` round-tripping, attempting to directly instantiate `ExecOutcome` failed because the struct is `#[non_exhaustive]` and external to the `tests` crate. The test was refactored to check `Message::Exit(i32)` directly, which circumvents the issue while properly validating the serialization logic.

## Privileged Test Runner implementation
- Implemented `imp-test-runner` to support running privileged integration tests without invoking `cargo test` under `sudo`. This binary is explicitly configured as the Cargo test runner for the test suite.
- It verifies that it has `CAP_NET_ADMIN` and `CAP_SYS_ADMIN` file capabilities (or `euid == 0` via setuid), drops its bounding set to the bare minimum, elevates these capabilities into the Ambient set, and correctly switches its `euid`, `egid`, and groups to the developer's identity before using `execve` to launch the actual test binary.
- This allows test binaries to inherit exactly the required capabilities for operations like TAP device setup or egress interception, without exposing full root access.

## Guest Agent Protocol Connection Bug
- During the test runner integration, tests in `exec_vsock.rs` failed with `Timeout("Agent connection timed out")`.
- **Root Cause**: The `AgentClient::connect` routine in `src/agent/mod.rs` was using a Tokio `BufReader` to read the initial `OK <port>\n` handshake string over the vsock connection. After reading the string, the `BufReader` was discarded, and the raw stream was passed into a `Framed` codec. If the guest agent sent the initial `Ready` framed payload immediately after the `OK` line, `BufReader` would pre-fetch those bytes, resulting in them being silently dropped when the reader was discarded.
- **Resolution**: We rewrote the connection handshake to perform exact 1-byte asynchronous reads (`stream.read(&mut byte)`). This prevents buffering and ensures that no bytes from the framed protocol payload are accidentally consumed and discarded. The entire test suite, including the privileged suite, now passes reliably.

## Rootfs Construction (OCI & mmdebstrap Builder VM)
- **In-Memory OCI Whiteout Application**: To handle multiple OCI layers efficiently without extracting to disk, we modified `tar2erofs.rs` to take an iterator of `tar::Archive` streams. It now correctly parses OCI whiteout files (both standard `.wh.filename` deletions and opaque `.wh..wh..opq` directories) directly in-memory, mutating the node tree before final EROFS generation.
- **Micro-VM Bootstrapping Independence**: The design specified that the builder VM boots on an OCI-built rootfs. Because the `Pipeline` builds the rootfs stage independently without external dependencies, the `MmdebstrapVm` source dynamically invokes `oci::build_rootfs` to build its own transient `builder_rootfs.erofs` before booting the `TestVm`.
- **Guest Agent Execution Timeout**: While executing `apt-get install -y mmdebstrap` and running the bootstrap script inside the micro-VM, we found that the guest agent's hardcoded 30-second `exec` timeout was frequently exceeded. 
  - **Resolution**: We increased the hardcoded `AgentClient::exec` timeout from 30 seconds to 10 minutes (`600` seconds) to safely support long-running build commands over the vsock connection.

## Firecracker VMM Backend
- We implemented the Firecracker VMM backend (`src/vmm/firecracker.rs`) as specified in the design.
- **Capabilities trait addition**: The design document specified that VMM capabilities (such as whether virtio-fs or nested virt is supported) should be exposed via a `capabilities()` method on the `Vmm` trait. However, this method and the `VmmCapabilities` struct were missing from the initial codebase. We added this explicitly to the `Vmm` trait in `src/vmm/mod.rs` and implemented it for `CloudHypervisor`, `FakeVmm`, and `Firecracker`.
- **API Communication**: Instead of relying on an external SDK (like `firecracker-rs-sdk`), we implemented the REST client manually using `hyper` over Unix domain sockets, just as the `CloudHypervisor` backend does. This minimizes extra dependencies and keeps the VMM HTTP logic localized and simple.
- **Boot sequence API calls**: A notable difficulty is that Firecracker does not allow a single payload for VM configuration like Cloud Hypervisor (`PUT /api/v1/vm.create`). Instead, we have to make multiple sequential `PUT` API calls to endpoints like `/machine-config`, `/boot-source`, `/drives/rootfs`, `/network-interfaces/eth0`, `/vsock`, and `/logger` before calling `PUT /actions` with `InstanceStart` to boot.
- **Vsock connection handling**: Because the `AgentClient` vsock handshake in `src/agent/mod.rs` was already updated during recent bug fixes (implementing strict byte-by-byte reading over the vsock connection and handling the exact "Firecracker-style hybrid-vsock handshake"), no changes were needed to the guest agent protocol to support Firecracker.
- **Cargo Installation Findings**: We attempted to compile Firecracker via `cargo install --git ...` but this fails due to strictly pinned internal dependency versions and C-compilation warnings (`-Werror`). We verified from the Firecracker documentation that it is designed to be built reproducibly via a custom containerized toolchain (`tools/devtool build`), not a naked Cargo install on the host. We abandoned `cargo install` for Firecracker and reverted to managing it as an external pre-compiled binary. The `README.md` was updated with the correct `curl` installation steps for Debian/Ubuntu.
- **Virtio PCI vs MMIO**: Following the v10 design revision, we enabled `CONFIG_VIRTIO_MMIO=y` in the guest kernel (via `microvm_config`) and run Firecracker in its native MMIO mode (without the `--enable-pci` flag).
- **Snapshot and Restore Limitations**: Because Firecracker is now running in MMIO mode instead of PCI mode, Firecracker's snapshot/restore functionality is supported. We updated `firecracker.rs` to report `snapshot_restore: true` in its `VmmCapabilities`.
- **Parallel Integration Tests (VMID Collisions)**: When running integration tests in parallel via `cargo test`, both `test_boot_ch` and `test_boot_fc` (and others) were occasionally failing with socket binding conflicts. This happened because `VmidAllocator::new()` was being instantiated locally per-test, causing multiple concurrent tests within the same `std::process::id()` to spawn VMs with identical VM IDs (e.g., `vmid = 1`), resulting in identical temporary directory paths (`imp-vm-<pid>-1`). We fixed this by refactoring `VmidAllocator` in `src/orchestrator.rs` to rely on a global `Mutex<Vec<u32>>` static variable, ensuring VM IDs remain truly unique across the entire test runner process regardless of parallelism.

## QEMU VMM Backend
- We implemented the QEMU VMM backend (`src/vmm/qemu.rs`) as specified.
- **vhost-user networking and QEMU**: We encountered multiple issues integrating our rootless `vhost-user-backend` with QEMU:
  1. `rust-vmm/vhost-user-backend` checks for `PROTOCOL_FEATURES` on `SET_VRING_ENABLE`, but QEMU often incorrectly sends `SET_VRING_ENABLE` *before* `SET_FEATURES` has finalized the negotiation. This caused our smoltcp daemon to exit immediately with an `InactiveFeature` error.
  2. The `vhost` crate also implements a similar strict `PROTOCOL_FEATURES` check on `SET_VRING_ENABLE`. 
  To fix this, we locally vendored both `vhost-user-backend` and `vhost` (via `[patch.crates-io]`) and commented out the strict `PROTOCOL_FEATURES` check when processing `SET_VRING_ENABLE`.
  3. We had to keep `PROTOCOL_FEATURES` in our advertised features, otherwise QEMU `vhost_net_start` fails with `-EINVAL`.
  4. We disabled `VIRTIO_NET_F_MRG_RXBUF` and `VIRTIO_NET_F_MQ` in the smoltcp backend to avoid compatibility issues with our custom RX queue processing, which isn't injecting `num_buffers` correctly.
  5. QEMU's `microvm` machine type uses `virtio-net-device` (MMIO) which falls back to legacy virtio header sizing (10 bytes instead of 12 bytes), causing networking to be silently broken as packets were offset by 2 bytes. We changed the QEMU machine type to `q35` and used `virtio-net-pci`, which cleanly supports the expected 12-byte headers and correctly brings up the network interface.

## Snapshot/Restore VMM Specific Bugs
- **QEMU `vhost-device-vsock` limitation**: In `test_snapshot_restore_qemu`, tests were hanging on restore. We investigated and discovered that QEMU relies on the external stateless `vhost-device-vsock` daemon for rootless vsock proxying. The stateless `vhost-device-vsock` proxy daemon does not support `vhost-user` state migration, which means the vsock queues are reset and desynchronized from the QEMU guest during a restore. Since QEMU cannot support snapshot/restore over vsock in rootless mode, we explicitly set `snapshot_restore: false` in `src/vmm/qemu.rs` `VmmCapabilities`.
- **Firecracker FPU XSAVE restore panic**: We temporarily switched the `RootfsStage` base image from `debian:bookworm-slim` to `ubuntu:24.04`, which caused Firecracker to fail its snapshot tests with `Error: RunWithApi(MicroVMStoppedWithError(GenericError))` upon restore. Inspection of the guest kernel serial log revealed a `restore_fpregs_from_fpstate` kernel panic inside the guest during restore. This is a known issue where highly optimized `glibc` AVX instructions (used aggressively by Ubuntu 24.04's libc) enable the extended FPU state (XSAVE), exposing a bug in Firecracker's snapshot/restore CPU state handling. We fixed this by reverting the OCI image back to `debian:bookworm-slim` (whose older libc does not eagerly trigger this bug), and the Firecracker snapshot/restore tests now pass again.

## Cloud Hypervisor and mmdebstrap Fixes
- **mmdebstrap Tarball Creation**: Replaced in-memory `ErofsBuilder` streaming with standard `mmdebstrap` tarball extraction using a temporary directory, and then processing the tar stream. This was necessary because `pack_erofs_with_injection` expects an actual tar stream from a file.
- **vhost-user Hang on Boot Failure**: When Cloud Hypervisor crashed or failed to boot, the test suite would hang indefinitely. This occurred because `smoltcp`'s `vhost-user` backend blocked on `listener.accept()` waiting for a connection that would never arrive. This blocked the Drop implementation of `SmoltcpProcess` during panic unwinding. We fixed this by manually connecting to the `vhost-user` unix socket during `SmoltcpProcess::drop` to cleanly unblock the thread and allow the test to fail correctly.
